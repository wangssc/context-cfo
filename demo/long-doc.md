这是一个故意写得超长的说明文件。它没有使用任何小节标题，只是连续不断地堆砌文字，目的是让扫描器把它识别为「超长且无结构」的死重对象。在真实的 agent 配置里，这种文件往往是一段被遗忘的背景介绍，或者一段从别处复制过来的长篇说明，它既没有提供可执行的步骤，也没有清晰的检索锚点，却占据了大量的上下文窗口。

当这样的文字被注入到 system prompt 或者按需加载到上下文时，它消耗的 token 并不会带来对等的价值。一个专业的成本审计应该能够把这种文件单独挑出来，标出它占用的 token 区间，并且提示用户：这一段文字是否可以压缩、是否可以拆分成带标题的小节、是否可以移动到 references 目录里只在需要时加载，而不是永远常驻在上下文当中。

为了模拟真实的超长无结构文件，我会在这里连续重复若干段内容，每一段都在讲同一件事，只是换一种说法。这种重复本身就是一种死重，因为它没有增加任何新的信息，只是让文件看起来更充实。审计工具如果足够聪明，应该能够发现这种跨段落甚至跨文件的重复，并且把它们计入可砍量的清单。

现在开始讲第二件相关的事。第二件相关的事和第一件相关的事之间没有标题分隔，读者（无论是人还是模型）只能靠语感去判断话题是否切换了。这种没有结构的长文，检索效率极低，模型在处理它的时候需要花费更多的注意力去理解段落之间的逻辑关系，而这些注意力本可以花在真正的任务上。这就是为什么「超长无结构」被列为第一类死重。
